# 0010. Database schema migrations with Alembic

- **Status:** Accepted
- **Date:** 2026-08-30

## Context

US-1 introduces the first persistent data (a `Portfolio` and its `Holding` rows), so the
project now needs a way to create and evolve the PostgreSQL schema in a controlled, versioned,
repeatable way across local, CI, and future deployed environments. Calling
`Base.metadata.create_all()` at startup would create tables but cannot evolve an existing
schema (add/alter/drop columns) without data loss, and it leaves no history of how the schema
got to its current shape. A capstone graded on software-engineering rigor should manage schema
changes the way a professional team does.

## Decision

We will use **Alembic** (the migration tool from SQLAlchemy's authors) for all schema changes.

- Migrations live in `backend/alembic/versions/`, each a versioned, reviewable script with
  `upgrade()` and `downgrade()`.
- `alembic/env.py` pulls the database URL from application settings (`APP_DATABASE_URL`) and
  uses `Base.metadata` as the target, so migrations always target the same database as the app
  and **no credentials are stored** in `alembic.ini`.
- The running stack applies migrations before serving: the backend container command runs
  `alembic upgrade head && uvicorn ...` (the DB healthcheck gates the backend, so the database
  is ready first).
- **Unit tests do not use migrations.** They build the schema with `Base.metadata.create_all()`
  against an in-memory SQLite database (fast, no PostgreSQL needed). Migrations are exercised
  end-to-end by the CI integration job, which boots the real stack.

## Consequences

- **Positive:** Schema changes are explicit, versioned, code-reviewed, and reproducible;
  upgrades and rollbacks are first-class. The ORM models remain the source of truth, with
  migrations derived from them.
- **Positive:** No secrets in migration config; migrations and the app share one source of
  truth for the database URL.
- **Cost:** Every model change now requires a migration (authored or autogenerated then
  reviewed) — a small, worthwhile discipline.
- **Cost:** SQLite-in-tests vs. PostgreSQL-in-prod means the unit tests do not catch
  Postgres-specific schema issues; the integration job (real Postgres + `alembic upgrade head`)
  is what validates the migrations themselves.

## Alternatives Considered

- **`create_all()` at startup, no migrations:** simplest, but cannot evolve a schema safely and
  keeps no history — unacceptable once real data exists.
- **Hand-written SQL migration scripts:** full control, but no autogenerate, no ORM awareness,
  and more error-prone than Alembic.
- **A heavier migration framework / ORM change:** unnecessary; Alembic is the standard partner
  for the SQLAlchemy stack we already use (ADR 0001).
